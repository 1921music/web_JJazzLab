# JJazzLabのWeb向け伴奏生成エンジン

JJazzLabの伴奏生成ロジックを再利用し、TeaVMのWasmGCでブラウザから使えるようにする。最初の範囲は、コード進行・曲構成・スタイルを受け取り、標準MIDIファイル（`.mid`）のバイト列を返すところまで。FluidSynthは含めない。SoundFontを使った発音は別のプレイヤーで扱い、UIの設計は後で行う。

## 移植の進め方

明らかなUIや音源の実装を除き、モデル、伴奏生成、MIDI出力に関わるクラスを広めに対象として、まずTeaVMでコンパイルを試す。調査用の `classesToPreserve` でクラスを広く保持し、スタイル読み込みからMIDI出力までを実際に呼ぶ入口も用意する。クラスの保持だけでは各メソッドの本体まで解析されるとは限らないため、両方から依存を調べる。

上流の更新を取り込みやすくするため、Web固有の処理は専用モジュールに置く。コンパイルで見つかった依存は、DIやTeaVMの差し替えでまとめて解消できるものから対応する。既存のJavaソースの変更は、これらの方法で解消できない箇所に限る。

NetBeansのサービス探索やUI通知などは、既存のSPIや依存性注入（DI）を使ってWeb向けの実装を渡せるか検討する。呼び出し箇所が多い依存には、TeaVMの `SubstitutionPolicy` によるコンパイル時のクラス差し替えも候補にする。調査用の仮実装は、未対応の処理が実際に呼ばれたときに明示的に失敗させる。

## 最初の検証と計測

スタイルファイルの読み込みも移植範囲に含める。最初の実証では、YamJJazzが対応するスタイルファイルをブラウザ上のエンジンで直接読み込み、短いコード進行からMIDIを生成して既存のプレイヤーやDAWで再生する。まず1スタイルで確かめる。出力はGeneral MIDI（GM）を想定し、音符、タイミング、音色指定、ドラムの割り当てをJVM版と比較する。ランダムな選択が比較に影響する場合は、選択条件を揃える。

最初は配信サイズを優先する。MIDI生成の入口に絞ったビルドで、Wasm本体、ローダー、スタイルデータの圧縮後の転送サイズをそれぞれ測る。速度も、初回の読み込み・初期化と、スタイル読み込み後の再生成を分けて記録する。数値目標は最初の実測を見て決める。

## 開発環境

Ubuntu 24.04 LTSをベースに、WSL 2の `wasm_jjazzlab_dev` を用意する。開発ツールはJDK 25、Maven、Git、rsyncを基本とし、TeaVMはMavenで管理する。

ソースの正本はWindows側の既存cloneとし、編集とコミットもそこで行う。ビルド直前にWSL内の作業コピーへrsyncで一方向に同期し、MavenはWSL内のファイルシステム上で実行する。同期から `.git`、`WSL_image/`、各モジュールの `target/` を除外し、Mavenのキャッシュとビルド生成物はWSLに置く。

VHDXの配置先は以下とする。

```text
G:\work\20261029\1921music\web_jjazzlab\WSL_image\wasm_jjazzlab_dev\ext4.vhdx
```

環境構築用のPowerShellスクリプトには、ディストリビューションの構築と、引数による登録解除・VHDX削除を用意する。削除時は対象の登録が指定のVHDXを指していることを確認する。
